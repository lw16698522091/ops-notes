综合模拟演练

一、演练目标

将服务管理、端口判断、磁盘排查、内存排查、日志分析串成一条完整的故障处理链路，模拟真实工作环境中的一次排障全过程。

二、演练场景

环境为 Nginx 反代 Tomcat，外部用户反馈访问站点失败。要求按真实排障流程定位问题并恢复服务。

三、故障初始现象

宿主机浏览器访问 http://192.168.149.128 返回 502 Bad Gateway。

四、排查过程

第一步 确认 Nginx 状态和端口

systemctl status nginx
确认 Nginx 本身运行正常

ss -lntp | grep 80
确认 80 端口监听正常

结论：Nginx 没有问题，问题在后端。

第二步 检查 Tomcat 状态和端口

systemctl status tomcat
发现 Tomcat 状态异常，显示服务已停止

ss -lntp | grep 8080
没有任何输出，8080 端口无人监听

结论：Tomcat 挂了，502 的原因确认。

第三步 查 Tomcat 日志找原因

journalctl -u tomcat -n 50
看到服务退出前的日志，但没有直接看到明确报错

继续用系统日志确认是否被系统杀掉：

dmesg | grep -i oom
发现 OOM Killer 的记录，确认 Tomcat 是被系统因内存耗尽杀掉的

第四步 查内存状况

free -h
发现可用内存极低

top 按大写 M 排序
没有发现特别异常的进程占用内存

结论：内存耗尽不是单个进程异常导致，可能是整体资源问题。

第五步 查磁盘

df -h
发现根分区使用率 100%

du -sh /var/log 排查日志目录
确认日志文件将磁盘写满

第六步 确认关联关系

磁盘满导致日志轮转失败，日志持续写入占满磁盘
服务运行需要的临时文件无法创建，最终引发内存耗尽，触发 OOM Killer 杀掉 Tomcat

完整链路：

磁盘满 → 日志写入异常 → 服务运行受影响 → 内存耗尽 → OOM 杀进程 → 外部访问 502

五、处理过程

清理磁盘

du -sh /var/log 2>/dev/null | sort -rh | head -5
找到占空间的日志文件，确认可清理后清空或删除

df -h 确认释放成功，使用率下降

重启 Tomcat

systemctl start tomcat
ss -lntp | grep 8080 确认 8080 端口重新监听

验证恢复

宿主机访问 http://192.168.149.128 恢复正常
systemctl status tomcat 显示 active（running）

六、复盘

1. 排障顺序非常关键
   先看 Nginx，再看后端，再顺着日志往下查，一步步找到根本原因

2. 表面原因和根本原因不同
   表面现象是 Tomcat 挂了，直接重启就能临时恢复
   但重启后磁盘问题还在，很快会再次崩溃
   必须找到根本原因（磁盘满）并处理，才能真正解决问题

3. OOM 现象迷惑性大
   服务看着像自己崩溃，实际是系统保护机制杀掉
   不查 dmesg 就会漏掉真正原因

4. 资源问题之间会相互诱发
   磁盘会引发服务异常，服务异常会引发内存问题
   排查时不能只盯着一个资源指标
